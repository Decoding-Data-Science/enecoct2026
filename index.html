Seven parts. Short tasks drop a part; important tasks keep all seven.

What is a Large Language Model?

A model trained to predict and generate sequences of language

Promptinstructions + question
Tokenstext broken into units
Modellearned patterns
Next-token probabilitieslikely continuations
Responseone token at a time
It learns patterns

Words, concepts, relationships, code structures and common language patterns from very large corpora.

It receives context

Your prompt + system instructions + conversation + retrieved documents + tool results.

It generates output

One token at a time, choosing likely continuations given the context. This is why it can be fluent and still wrong.

Simple mental model

An LLM is a powerful language engine — not a database of guaranteed facts.

LLM foundations in practical terms
ConceptPractical meaning
PromptThe instruction and context sent to the model.
TokenA unit of text used by the model; token limits affect context size and cost.
Context windowThe amount of information available to the model for one interaction (e.g. gpt-4o-mini: 128K tokens; gpt-5.4-mini: 400K).
TemperatureControls output variability; lower values are usually preferred for bounded enterprise tasks.
Structured outputA predictable schema such as JSON, useful for downstream systems.
HallucinationA fluent answer that is unsupported, invented or incorrectly grounded.
Foundation modelA general-purpose model that requires instructions, evidence and application controls.
Why an LLM alone is not enough for enterprise AI
1. May not know your data

Private policies, current procedures and records aren’t in the model.

2. Knowledge changes

Procedures, work orders and system state change after training.

3. Generates confidently

Fluency ≠ factual correctness or authority.

4. Needs evidence

Users need sources, citations, provenance and document authority.

5. Cannot act by itself

Querying systems requires controlled tools.

Opening question

Ask a general LLM: “Which inspection procedure is currently approved for A-001?” It cannot reliably know. That limitation motivates RAG (knowledge grounding) and tools (actions and live system interaction).

What is an AI agent? (preview of Day 3)
LLM / reasoning model

Chooses the next step based on goal and context.

Goal + instructions

What must be achieved? What rules must be followed?

Tools

RAG, SQL, APIs, code, calculators, workflows.

Observation / state

Tool results become new context for the next decision.

THINK → ACT → OBSERVE → THINK AGAIN

RAG is not the whole agent

RAG is a retrieval-and-generation pattern — used directly in Q&A or exposed as one tool to an agent. The agent decides: need documents → RAG; need structured values → SQL; need an external system → API; enough evidence → answer; not enough → ask or escalate.

Generative vs reasoning-optimised models

A useful mental model — not a strict two-box taxonomy

Fast / general generation

Optimised for broad conversation and content generation. Usually prioritises speed and cost efficiency.

summarisingrewritingextractingdraftingstraightforward Q&A
Deeper reasoning

Optimised to spend more computation on difficult multi-step problems. Often slower and more expensive; may expose different controls (e.g. reasoning effort) and ignore some sampling parameters.

planningcomplex logicmulti-step analysiscoding / debuggingdifficult tool-use decisions
Reality

Capabilities overlap — it’s a spectrum. Choose the model based on task, latency, cost, accuracy and governance: “What quality do I need, at what latency and cost?” A simple extraction task rarely needs the most expensive reasoning model.

Interactive · what is temperature?

A generation setting that influences how deterministic or varied token selection is. Below: an illustrative next-token distribution for the prompt “The currently approved A-001 inspection procedure is version …”. Move the slider and sample.

T =0.70
Low temperature

More consistent / deterministic. Extraction, enterprise Q&A, structured answers, repeatable workflows.

Medium

Balances consistency with some variation. Normal chat, explanations, controlled brainstorming.

High temperature

More variation / creativity. Ideation, creative writing, diverse suggestions.

For grounded enterprise RAG we usually want consistency more than creativity. Exact temperature behaviour and supported ranges vary by model/provider.

Embeddings — useful mental model

An embedding turns text into a numeric vector so semantically related text can be compared — even when exact words differ.

meaning → vectors
"How much annual vacation do employees receive?"
   → embedding model → [0.021, -0.14, 0.51, …]

"Employees receive 30 calendar days of annual leave."
   → embedding model → [0.018, -0.13, 0.49, …]   ← close!
Non-negotiable rule

Document vectors and query vectors must use the same model and the same dimensionality. A 512-dim query cannot be compared with 1024-dim document vectors.

Cosine similarity in NumPy
retrieve()
vector_store = create_embeddings([c["text"] for c in chunks])
vector_store /= np.linalg.norm(vector_store, axis=1, keepdims=True)

def retrieve(question, top_k=4):
    q = create_embeddings([question])[0]
    q = q / np.linalg.norm(q)
    scores = vector_store @ q           # cosine = dot of unit vectors
    best = np.argsort(scores)[::-1][:top_k]
    return [(chunks[i], float(scores[i])) for i in best]

Retrieval strategies
Lexical · TF-IDF / BM25

Strong for exact terms, IDs and procedure language (“HR-2026-117”). Easy to explain and debug. Can miss synonyms.

Semantic · embeddings

Strong for paraphrases and concept similarity. Can retrieve conceptually similar but non-authoritative content.

Hybrid · combined

Balances lexical and semantic signals with enterprise metadata. Best for mixed enterprise query styles.

Hybrid ranking formula (Governed RAG masterclass)

score = 0.80 × bm25 + 0.15 × authority + 0.05 × entity

Eligibility first. Ranking second. Generation last.

Core governance trap

Relevant does not automatically mean trusted

The newest or most semantically similar document is not automatically authoritative. V3D is newer but DRAFT; V2 remains the current APPROVED procedure.

Superseded

V1 · A001-PROC-INS-001-V1

Version 1.0 · 2025-03-01. Historical comparison only. Ranks well lexically because terminology is almost identical. Lacked trend comparison, version verification, evidence-gap recording.

Approved · current

V2 · A001-PROC-INS-001-V2

Version 2.0 · effective 2026-02-01. Current procedural authority — six-step evidence-oriented workflow, evidence checklist, interpretation rules, required briefing output.

Draft

V3D · A001-PROC-INS-001-V3D

3.0-draft · 2026-08-20. NOT approved. Proposes auto “Priority Review” labels (open reviewer comment: may bias reviewers). Newer ≠ approved.

Notebook Day2_01 · GenAI basics and RAG from scratch

Chunk, embed, retrieve, answer with citations, all visible

The smallest complete RAG application on the real course documents: no vector database, no framework. The NumPy matrix is the vector store and every step prints what it did.

Setup time · run once
  1. Clone the repo, load the Markdown documents
  2. Attach doc ID, version and status to each document
  3. Split into chunks by section
  4. Embed every chunk
  5. Stack the vectors into a NumPy matrix
Question time · every question
  1. Embed the question
  2. Cosine similarity against every chunk
  3. Keep the top chunks (APPROVED first)
  4. Send question + chunks to the chat model
  5. Return the answer with document IDs
Day2_01 · core of RAG from scratch
client = enec.get_client()                 # key from Colab Secrets
MODEL  = enec.pick_model(client)

def embed(texts):
    r = client.embeddings.create(model="text-embedding-3-small", input=texts)
    v = np.array([d.embedding for d in r.data])
    return v / np.linalg.norm(v, axis=1, keepdims=True)

M = embed([c["text"] for c in chunks])      # the whole vector store

def retrieve(question, k=4):
    scores = M @ embed([question])[0]
    return [chunks[i] | {"score": float(scores[i])} for i in np.argsort(scores)[::-1][:k]]

def answer(question):
    ctx = "\n\n".join(f"[{c['doc_id']} v{c['version']} {c['status']}]\n{c['text']}" for c in retrieve(question))
    msg = [{"role": "system", "content": "Answer only from the sources. Cite [doc_id]. "
                                         "If the sources do not answer, say so."},
           {"role": "user", "content": f"QUESTION: {question}\n\nSOURCES:\n{ctx}"}]
    return client.chat.completions.create(model=MODEL, messages=msg, temperature=0).choices[0].message.content

Notebook Day3_02 · a decision tree as an agent tool

Train and judge a model on log windows, then let the agent call it

Each 15-minute window per asset is summarised by 16 counts from the logs (failed logins, distinct ports, bytes out, unapproved commands...). A decision tree learns which patterns look like attacks. The agent gets the tree as a read-only tool and puts flags in a human review queue: the tree is a triage aid, not a verdict.

Test set: last 9 days (confusion matrix)

A model that always says “normal” scores accuracy and catches nothing. Judge by recall (attacks caught) and precision (alarms that were real).

Reading a price
  • Input: everything you send: system prompt, question, retrieved chunks, tool results.
  • Output: what the model writes back. Usually 4 to 8× the input price.
  • Cached input: a repeated prompt prefix (same system prompt and context) billed at a discount.
  • 1 million tokens ≈ 750,000 English words.
Where course money actually goes
  • Embeddings: tiny (fractions of a cent per run).
  • RAG answers: input-heavy (retrieved chunks), small output.
  • Agents: several model calls per question, each carrying the growing conversation.
  • Capstone briefing + LLM judge: the largest single calls.

Why an older, smaller model is enough here
  • The evidence does the heavy lifting. RAG, SQL and tools put the facts in the prompt; the model reads and cites them.
  • Bounded tasks. Classify, extract, summarise, route to a tool, fill eight sections. These are well within a small model's ability.
  • Consistency. With temperature 0 and a strict format, small models give stable, checkable answers.
  • Speed. Faster replies keep a live class moving and agents responsive.
  • Cost. 20 people iterating all day stays in single-digit dollars.
  • Availability. Older models work on almost every API key, so nobody is blocked.
When to step up to a larger model
  • Long, open-ended investigations with many steps and conflicting evidence.
  • Generating or refactoring non-trivial code.
  • The small model keeps failing your evaluation set after you fixed retrieval and prompts.
  • High-stakes summaries where a human reviewer still checks, but quality must be higher.
Rule of thumb

Fix the evidence first, then the prompt, then the model. A smaller model with the right context beats a huge model with the wrong context.

def run_sql(sql):
    q = sql.strip().rstrip(";")
    if not q.lower().startswith(("select", "with")) or ";" in q \
       or re.search(r"\b(insert|update|delete|drop|alter|create)\b", q, re.I):
        return "REJECTED: one read-only SELECT only"
    con = sqlite3.connect("file:ENEC2026_Asset360.db?mode=ro", uri=True)
    return pd.read_sql(q, con).head(50)
